# Stage 1 Implementation Plan: One Song, Played to the End

Scope: the stage 1 row of the roadmap (design.md:951): chart loading, input, audio, a simple play screen, an evaluator with one custom preset, saving the input log, key config, volume, offset, hi-speed, instant retry, and the testing mechanisms (design.md:96-104). Exit: one chart on hand plays to the end without felt latency or stutter, and key sound and frame latency are measured and displayed.

Citations: `design.md:N` is `docs/design.md` as of commit d34ef8d (line numbers drift as the design is updated; the section names stay); `spike/...:N` is branch `spike/stage0`; "S0 results" is the stage 0 results comment on issue #3. Every other path is repo-relative.

Direction applied throughout: every extension point exists as a named trait or enum with one implementation and core calls through it (design.md:593); nothing else is built ahead; measured numbers are indicators, never gates (design.md:80, 444); verification only on the development PC (design.md:442); a later variation that hits a flaw rebuilds the affected part (design.md:79).

## 1. Decisions

Each decision names the alternative it beat. "Tuned by playing" marks a default whose value is a starting point the developer changes by playing (design.md:77). Safety caps (D14) are not tuned by playing: they bound work on untrusted files, sit far beyond real charts, and are never indicators.

### D2. Chart model shape

`Chart` is fully resolved and in integer µs: per-lane `Vec<Note>` sorted by time (`[Vec<Note>; 8]`, lane 0 scratch, 1-7 keys), a separate `bgm: Vec<BgmEvent>`, `sounds: Vec<SoundRef>` (the `#WAV` table: the name as written, and the resolved path confined to the chart folder; D14), `bar_lines`, `scroll: ScrollMap`, `meta` (title, `#RANK`/`#DEFEXRANK`, `#TOTAL` as thousandths, chart LN mode if declared) and `identity` (SHA-256 and MD5 of the file bytes, resolved-chart hash, loader version, `#RANDOM` branch results). The resolved-chart hash covers the resolved objects and the sound names as written, never resolved absolute paths, so moving a chart folder does not change its identity. `NoteKind` is `Tap | Long { end, end_sound } | Mine { damage }`.

- Per-lane vectors because the evaluator works per lane with a cursor at the first unprocessed note (design.md:869-870) and rendering finds the visible range per lane (design.md:867, 481).
- Alternative: one time-sorted event list keeping BMS measure positions. Every consumer would redo the rational conversion, and the evaluator would see notation instead of time. design.md:280 asks the loader to reconstruct LN spans, not the evaluator.
- `ScrollMap` is the piecewise linear function from time to display position built at load (design.md:867), integer positions in millionths of a beat. STOP segments have slope 0.
- `bms-model` uses no floating point (crates/bms-model/src/lib.rs:7-8). The renderer converts positions to pixels in `f32` on its own side.

### D3. Rational time computation

Time is accumulated per segment between BPM changes and STOPs as an exact rational of arbitrary-precision integers (`num_rational::Ratio<num_bigint::BigInt>`), and each object's time is converted to µs once with mathematical floor and narrowed to `i64` with `try_from` (design.md:152, 846, 866). The value is exact, so each time equals the one any other exact representation gives. A STOP's length in the scroll map is `floor(end) − floor(start)`.

- Decimal values: BPM, measure length (`#xxx02`), `#STOP`, `#TOTAL` and `#DEFEXRANK` are parsed from the trimmed text straight into rationals. The text must match `[+-]?(?:[0-9]+(?:\.[0-9]*)?|\.[0-9]+)(?:[eE][+-]?[0-9]+)?`, so `.5`, `2.`, `+1`, zero-padded digits and `1.00001E+07` are accepted, and commas, inner whitespace, `NaN`, `Infinity` and hex floats are not. The value is `digits × 10^(exponent − fractional digits written)`. Leading and trailing zeros that do not change it are not counted: `0012.50e1` has 3 integer digits and no fractional ones. Counted that way, the value has at most 12 integer digits, and a positive exponent is at most 18 (its own leading zeros do not count). Digits past the 18th fractional one are cut off, rounding toward zero, the same way every time. A negative exponent only moves digits past that point, so it may be larger, up to 18 digits long; `1E-100` becomes 0. Every bound is checked on these counts before any number is built, so a long run of digits costs a scan and nothing more. Every value is then `n / 10^18` with `|n| < 10^30`.
- Timing values outside that, a BPM below 0.000001 (`≤ 0` included) and a measure length `≤ 0` are load errors (design.md:866). A measure length of 0, as written or cut off to it, is refused because the measure has no length, so its timing is undefined. Time uses the exact BPM; the scroll map takes it in millionths rounded down, which the minimum keeps at 1 or more. `#TOTAL` and `#DEFEXRANK` are kept in thousandths rounded down; an invalid one (`1e19`) does not change timing, so it is ignored with a warning, like any other unreadable header value.
- Size cap: the running time is the only value that grows with the chart. Its reduced denominator divides the least common multiple of the denominators of every segment added so far, so distinct BPMs multiply in (20 distinct odd prime BPMs already pass 2^128). The text limits bound every other value. A position inside a measure is `index / count` of it, and a line has fewer than 2^23 slots in a 16 MiB file, so the span between two positions in one measure is a fraction with a denominator below 2^46. Measure lengths and BPMs are `n / 10^18` (10^18 < 2^60, `n` < 2^100), so a segment's µs, `Δbeats × 60,000,000 / BPM`, has a denominator below `2^46 × 2^60 × 2^100 = 2^206`, and a STOP's below 2^166. The time's denominator is capped at 16384 bits, checked after every addition, so the cap applies to the canonical order of additions (positions in order, bar lines first, then file order). The numerator stays within 32 bits of the denominator, because the duration cap (60 min, below 2^32 µs) is checked after every addition too. Exceeding the cap is a load error naming the measure.
- Cost: each position is one event, with one addition, and a second one when a STOP sits there. The time is added with the reduced-sum method (Knuth, TAOCP vol. 2, 4.5.1): it takes `gcd(denominator mod q, q)` and `gcd(t mod g, g)` against the term's denominator `q` only, and builds the reduced result without normalizing it again; num-rational's own addition takes a GCD of two full-size numbers instead. At the cap the time has 256 64-bit limbs and a term at most 4, so an addition is about seven passes of 256 × 4 limb products plus the floor division, about 8,000 limb operations. D14 allows 501,000 positions and 500,000 objects, so at most about 1,000,000 additions: an estimate of 8 × 10^9 limb operations, several seconds. Measured on the development PC (release build), a heavy fixture at the cap (the denominator driven to 16371 bits first, then 480,000 notes each adding a small term) loads in 3.9 s, against 0.8 s for about as many events with a small denominator; that time describes this fixture, not every chart the limits allow. A chart may use every hex BPM (channel 03, all 255 values: least common multiple 362 bits) together with about 800 further pairwise-coprime BPMs of the form `ddd.ddd`. Admitting every chart within D14 does not fit the chosen loading budget: the 1295 `#BPMxx` definitions alone reach about 130,000 bits.
- Fixed rules, written down as loader behavior: at one position a BPM change applies before a STOP (the STOP length uses the new BPM); a note at a STOP's position sounds at the STOP's start; extended BPM (`#BPMxx`, channel 08) and channel 03 are both read, and channel 08 wins at the same position. Loader version 2 brought the decimal grammar above, and with it `#TOTAL` values that version 1 ignored.
- Alternative: `Ratio<i128>` with checked operations. The denominator overflows on charts with many distinct BPMs, which then cannot load. Alternative: fixed-point `i128` time in sub-µs units. Each segment rounds, so results drift from the exact times (some objects land on a different µs), more with every segment. Alternative: accumulate integer µs per segment, the same drift at a coarser unit. Alternative: `f64`. Results depend on operation order and platform, and determinism is a principle (design.md:39).
- Allocation: big integers allocate on every operation. Time is computed only while loading (`load_bms`, called from `game`'s chart preparation before the session), and the chart model holds only `i64` µs, so nothing in play allocates for it.
- An exceeded cap is a load error naming the measure, never a wrap.

### D4. The evaluator's event queue

Three kinds of head feed one fixed-order scan, without a heap (design.md:869):

- **Chart deadlines, built at preparation.** `Evaluator::new` builds one chronological deadline array per lane from the chart and the preset: tap miss deadlines (note time + late BAD edge), LN release deadlines (LN end), mine times, each sorted by `(time, kind)` with the kinds in that order (miss, LN end, mine). Note times being sorted does not make deadlines sorted (a tap at 1000 ms misses at 1180 ms, after a mine at 1100 ms), so the arrays are sorted explicitly. Plus one song-end deadline (D13), after every other deadline at its time. Each deadline is skipped by its own condition when reached: a tap miss deadline if that tap was judged; an LN release deadline if that LN is finished (completed, broken, or its head missed; a judged head does not finish it, and an unjudged head lets the deadline pass without effect); a mine deadline never.
- **Input-dependent deadlines**, which input creates or moves during play and which therefore cannot be prepared: the pending scratch-release deadline per scratch control (PR18). They live as mutable fields in the conversion state and take part in the same scan.
- **The input stream**, in the order `eval::merge` produced: sorted by `(evaluation time, source index, per-source sequence)`. The evaluator never reorders inputs, by lane or by press and release.
- The scan compares the input head, the 8 lane deadline heads and the pending conversion deadlines by `(time, kind, lane, seq)`. At equal time, inputs come before deadlines, so a press exactly on the late edge of a window counts. This order is a preset item (`SameTimeOrder::InputsFirst`; design.md:264, 274).
- Alternative: a `BinaryHeap` of all deadlines. It allocates as deadlines are pushed, needs an explicit tie key anyway, and costs `log n` for streams already built in order.
- The live logic thread and batch `evaluate` call the same `merge` and the same constructor, so they cannot diverge (design.md:217, 888).
- `push_input` appends to a ring sized at construction and `advance_to` writes into a caller-owned `Vec` with reserved capacity, so neither allocates during play (design.md:858-860).

### D5. Fixed-point gauge

`GaugeValue(i64)` in units of 1/100000 % (1 % = 100_000, 100 % = 10_000_000), intermediate products in `i128`, order fixed as "compute the change → clamp to the bounds", remainders floored (design.md:873). With `#TOTAL` in thousandths, the per-note increment is `floor(total_milli × 100 / judgeable_notes)`. Survival gauges stop at 0 and record `failed_at`, and a reference trajectory continues in separate state (design.md:308-311).

- Alternative: `i32` in 1/100 %. Per-note increments of `TOTAL/notes` for long charts fall below the unit and round to 0. Alternative: `f64`. Forbidden in `eval` (crates/eval/src/lib.rs:10-15).

### D6. Input recording, sources, and the log format

**Sources.** One physical device is one source: it owns one queue, one input latency offset, and all its controls, buttons and axes alike (design.md:216). Several keyboards are several sources. Sources get anonymous session-local ids (0, 1, … when recording opens: controllers first, then keyboards, each in the order found, so a keyboard's many Raw Input handles never push the controller out at the source limit). Only devices the key config plays take part: every keyboard, and the configured controller (D10). Devices that take part but find no source are counted and named on the console before the countdown; with many keyboard handles one of them may carry lanes. An axis is recorded only if its source declared it when recording opened: one a collection adds during the play is not recorded until the next. A replayed log declares the axes its record binds. Interface paths, names and serials never enter the log. Keyboard bindings are by scan code and may be shared by every keyboard; the binding is shared, the sources stay separate. The set of participating sources is frozen when recording opens and does not grow during the play. Source bookkeeping is preallocated with a fixed maximum; a device beyond it does not take part, and the log records that as `incomplete`.

**What is recorded.** Only controls bound in the key config (lanes and system controls), while play recording is open. Unbound controls cannot affect evaluation, which applies the recorded bindings (design.md:200), and a log then never holds typed text. While recording is closed, the key config screen (PR16) may capture any control to bind it; nothing captured there is recorded. PR5 writes this section's contract into design.md before any of it is implemented (D6 as a whole; see PR5).

**Events.** `PhysicalInputEvent { received, source, kind }` with `InputKind::Control { control, value } | Disconnected` (design.md:210, 338). `received` is the true receive time: the floor of the QPC read when the batch was received, the same for every event of the batch (design.md:119, 144). A `Disconnected` event releases every held control of that source in input conversion and clears its state, identically live and in re-evaluation. A removed source publishes its removal time as its final watermark and is closed, but it stays in the minimum of design.md:217 until all its queued and staged events are merged; then it is retired, so a removed device cannot stall the global watermark and loses no event. Removing the last participating device aborts the play (D13). A device that arrives during play is lifecycle metadata only: its arrival time and kind go into a bounded arrivals list outside the input stream, the merge and the watermark, and it takes part from the next play. As an input event, its arrival could carry an evaluation time below the already finalized watermark, which design.md:191 rules out.

**Held-input snapshot.** The input thread keeps each device's physical state (pressed controls, last axis values) from the Raw Input it receives, for the whole run of the game, including across retries. A device whose state has not been seen since the game started counts as released, and a release of a control not held is a no-op in conversion. Recording opens at a boundary between two input-thread batches: the thread copies the per-device state of the participating sources into `InputStart { opened_at, held: Vec<(SourceId, ControlId, value)> }`, and every event it pushes after that point, in stream order, belongs to the play. `opened_at` is the QPC read at that boundary. Events of the next batch may carry the same microsecond, because the boundary goes by stream order, not by time. One function, `eval::ConversionState::init(device, &InputStart)`, sets up input conversion for both `Evaluator::new` and `evaluate`. A held control starts pressed with no press edge, so nothing is judged from it; its later release is a plain release (design.md:358).

**Focus loss (one policy).** Losing focus during play aborts the play. The window's focus-loss notification (`WM_ACTIVATEAPP` with `FALSE`, or `WM_KILLFOCUS`) sets a latch that the input thread checks before each batch. Independently, every Raw Input packet marked `RIM_INPUTSINK` (received while the game was in the background) is rejected before it can be recorded, and it trips the latch too. This catches focus changing between the latch check and the batch. Once the latch is set, the thread appends nothing more and signals the abort. The play ends at the last already finalized watermark (D13), recording closes, and the play is saved as "ended midway". A new play starts from the beginning.

**Format.** Custom binary (design.md:850): the magic `TPRL`, a `u16` format version, a `u8` body encoding (1 = zstd), a `u32` uncompressed body length, then the zstd-compressed body. The body is a fixed sequence of sections, each a `u32` length plus payload. Integers are LEB128 varints (zigzag for signed values), and input times are deltas from the previous event of the same source.

- The log holds the core parts (design.md:962): versions (format, evaluator, loader, app, and the build provenance `production | development`, design.md:929), chart identity (SHA-256, MD5, resolved hash, `#RANDOM` seed and branch results, and the chart transform as an id and a version), the preset record (id, SHA-256 of `canonical_bytes`, a copy of those bytes), the session policy id, the device profile used for evaluation (per source: kind, receive method, input offset, bindings; plus the audio and display offsets, design.md:173), play type (always full), `InputStart`, the physical input events including `Disconnected`, the arrivals list, and the status: end status, the finalized watermark at the end, and `incomplete` with its reason.
- Not in the log yet and added later with a version bump: report intervals and polling estimates, offset change segments, hi-speed and lane cover stream, practice fields, IR token. PR18 adds the axis bindings with their scratch settings as format version 2, and the count of axis values outside the range their conversion uses per source as format version 3. Before the first release, formats may change: each layout change bumps the version, the decoder reads only the current version, and older versions are refused with `UnsupportedVersion(n)`, not converted. Reading older versions starts with the first release.
- The preset is identified by the hash of its canonical binary encoding, not of the TOML text, so whitespace and comments do not split records. The encoding starts with its format version. Before the first release a layout change bumps it and only the current layout is written, so a record made under an older layout matches no preset and its re-evaluation is refused as a preset mismatch. A preset file of an older shape is refused when loaded, not converted (AGENTS.md).
- Alternatives: `serde` with `bincode` or `postcard`, where the wire layout follows Rust struct layout and changes silently with a field reorder; JSON, about 5-10× larger; protobuf, a schema compiler for a format with one reader and one writer. design.md:343 already rules out version detection by output hash.

### D7. The custom preset (all values and edge behaviors tuned by playing)

Values and behaviors are chosen by what the player experiences, and the developer changes them in the preset file between retries (D10).

| Item | First value | What the player experiences |
| --- | --- | --- |
| Judgment windows, early = late, one table for every lane | PERFECT ±20 ms, GREAT ±45 ms, GOOD ±100 ms, BAD ±180 ms | A press that feels on the beat is PERFECT. Clearly off but intended reads as GOOD, and only a wrong press is BAD |
| Miss | No press by the late BAD edge → POOR. A press that judges a note also passes every earlier unjudged note of its lane: each is a POOR at the press, in note order, before the press's own judgment, with the usual miss effects (a passed LN head loses its LN) | A missed note is decided as soon as it cannot be hit any more, and notes are never judged out of order |
| Empty POOR | A press that judges no note but has a note of its lane, judged or not, within 500 ms after it or 150 ms before it (both edges inclusive); mines are not notes here. Every such press counts, with no cap. No combo break, BP +1, not counted in judgment counts; gauge damage half of a POOR | Mashing early, or again right after a note, is noticed and costs a little, but does not end a combo |
| Combo | Broken by BAD and POOR | — |
| Note assignment | Nearest unjudged note inside BAD, ties to the earlier one, so a late press moves on to the next note once it is past the midpoint between the two, even inside the earlier note's GOOD window | An early press does not steal the next note |
| LN mode | LN: only the head is judged, as a tap | Holding to the end matters, but the release need not be exact |
| LN early release | Release earlier than end − 100 ms after a scored head: an "LN break". The head's judgment, counts and EX score stay; combo breaks, BP +1, gauge takes POOR damage, and `ln_breaks` +1. The LN is finished, and a re-press is an ordinary press on the lane | Letting go early costs the combo, not the score already earned |
| Late head after a short LN's end | A head pressed within its late window but at or after the LN's end is judged by its deviation, and the LN counts as completed at the press; the following release is ignored | Very short LNs behave like taps |
| Mines | Damage every gauge by the chart's value when the lane is held as the mine passes, at 0.5 percentage points per unit of the value (the chart's own unit; `1E` = 50 units = 25 %). The damage applies as is: the survival gauge's low-gauge halving does not reduce it. No judgment, combo or BP effect | — |
| Gauge denominator | Judgeable notes = taps + LN heads; mines excluded | — |
| `#RANK` scale | 0: 50 %, 1: 75 %, 2: 100 %, 3: 125 %; `#DEFEXRANK n`: n %; no rank, or a `#RANK` outside 0-3 (an extension this preset does not support): 100 %. Each window edge is scaled in µs and floored | Harder ranks shrink every window by one factor |
| `#TOTAL` absent | 160; a `#TOTAL` that is not positive counts as absent | An all-PERFECT play fills the normal gauge from 20 % to full at about half the chart |
| Normal gauge (decided at the end) | Start 20 %, clear 80 %, PERFECT and GREAT +TOTAL/notes, GOOD half of that, BAD −2 %, POOR −6 %, floor 2 % | — |
| Survival gauge | Start 100 %, PERFECT +0.16 %, GREAT +0.16 %, GOOD 0, BAD −5 %, POOR −9 %; damage is halved when the value before the change is below 30 % (exactly 30 % takes full damage; the halved change is floored with its sign, so −1.5 units become −2; mines are not halved) | — |
| EX score | PERFECT 2, GREAT 1 | — |
| Zero judgeable notes | `Evaluator::new` returns `EvalError::NoJudgeableNotes`, and the session refuses to start with that message | Nothing to play, rather than a division by zero |

- Each enum (`Assignment`, `LnMode`, `TotalMode`, `MineRule`, `SameTimeOrder`) gets only the variant this preset uses (design.md:287). The variants that later presets need arrive with them. A rule the custom preset no longer uses is removed with the code that evaluates it: before the first release, records made under an older preset are refused, not re-evaluated (AGENTS.md).
- One window table for all lanes. design.md:274 allows separate tables for scratch and LN ends, but no stage 1 preset needs them.
- Alternative: copy an existing player's numbers. design.md:284 says the custom preset differs, and a copy would carry another implementation's choices without the developer having felt them.

### D8. Threads and queues

Threads follow design.md:86-94: input (1 kHz high-resolution waitable timer, MMCSS "Games"), logic, audio (WASAPI event, MMCSS "Pro Audio"), render (waits on the swap chain's waitable object), main (winit), and loading (a bounded pool that ends before the countdown; D14).

- SPSC queues: `rtrb` (design.md:837). The spike ran it on every hot path with zero app allocations (S0 results; spike/app/src/threads.rs:14-15). Alternative: our own ring of about 150 lines of atomics, which we would then own and verify for no gain. Alternative: `crossbeam-channel`, an MPMC queue with heavier synchronization than one producer needs.
- Render snapshot: `triple_buffer` (design.md:838, MPL-2.0, already proven in the spike).
- Logic wake: `std::thread::Thread::unpark` from the input thread after each publication, and `park_timeout` on the logic side. This is portable, allocation-free, and survives a missed wake: the next wake advances to the latest watermark (design.md:252). Alternative: a Win32 event as in the spike (spike/app/src/threads.rs:158-190), which would make `game` Windows-only.
- Watermark protocol (design.md:216, 219). Producer: stamp the batch with the floor of the QPC read at receipt, push it, then read QPC afresh and store `w_i = floor(fresh QPC) − 1 µs` with `Release`. Any later batch takes its own QPC read after that, so it is stamped at or above the fresh value and can never fall at or below a published watermark. Receive times stay true, and events with equal receive times stay ordered by source and sequence. Consumer, each logic step: (1) load every source's `w_i` with `Acquire`; (2) pop that source's events into its staging buffer, stopping at the first event with receive time > `w_i`, which stays staged for the next step; (3) compute `W = min over participating sources not yet retired of (w_i − offset_i)` (D6); (4) merge staged events with evaluation time ≤ `W` and push them; (5) `advance_to(W)`. Events beyond `W` stay staged. Reading the watermark after popping would let a press pushed in between be skipped while its miss is finalized.
- Capacities are fixed at session start from the length of the recording window, which is capped (D14): countdown and lead-in, the chart, and finalization through the final deadline. Each lane-bound button gets room to be pressed and released 30 times a second over that window, at most 240 edges a second for all of one source's buttons together, and each lane-bound axis the source declares 1000 events a second (PR18); an axis it does not declare is never read. A system control (retry, quit) gets a press and a release in all, not a rate: its first press ends the play. So a keyboard bound only to retry and quit adds 4 inputs, whatever the window's length, and the many keyboard handles Windows exposes do not grow the window. A window beyond the recording budget refuses the play (D14). These rates size one capacity for the whole window, shared by every recorded control; none is enforced on its own. A burst fits while the window's total does and each source's queue (4,096 events) has room. A retry or quit key held across a retry auto-repeats in Raw Input while the window ignores the repeats, and may use up the capacity. Input beyond the capacity aborts the play at the last finalized watermark, with the end status "ended midway" (D13), and a full source queue drops the incoming event while the play goes on; either marks the log incomplete with the reason "overflow" (design.md:253).

### D9. How the play screen is drawn

wgpu on DX12 directly (design.md:410, 839), reusing what the spike proved: `Dx12UseFrameLatencyWaitableObject::DontWait` with the render thread waiting on the waitable object itself (spike/app/src/run.rs:183-190), `PresentMode::Fifo`, `desired_maximum_frame_latency = 1` (spike/app/src/window.rs:353-354), borderless fullscreen, independent flip in fullscreen (S0 results, "For stage 1"), one instanced sprite pipeline with alpha and additive blending over a texture atlas (spike/app/src/render.rs:118-160), and every pipeline and upload done before the countdown (design.md:494).

- The skin boundary: `render::PlaySkin` with one implementation, `SimpleSkin` (a hard-coded 16:9 layout authored at 1920×1080 and scaled; design.md:417). The declarative skin of stage 3 is a second implementation behind the same trait.
- Text: an ASCII 5×7 bitmap font defined in code and baked into the atlas at startup. It covers judgment names, combo, the measurement overlay and the key config prompts. Alternative: `cosmic-text` + `glyphon` (design.md:840). They need a font file and its license, and they exist for Japanese titles, which first appear on the song select screen of stage 2.
- No `egui` in stage 1. The only settings screen is key config, drawn with the play screen's sprites (PR16). Hi-speed, volume and display offset are keys during play. `egui` arrives with song selection and settings screens in stage 2 (design.md:843). Alternative: an `egui` settings overlay now, which brings three crates (`egui`, `egui-wgpu`, `egui-winit`) for four values.
- No BGA in stage 1. The roadmap's stage 1 list has none, and it brings FFmpeg, libclang and LGPL packaging (S0 results, "For stage 1"). It returns with "Look and effects" (design.md:953), where `spike/app/src/bga.rs` is the starting point.
- Hi-speed: the setting is the visible time in ms from a note's appearance to the judgment line, 600 ms at first (a first-time read is comfortable; tuned by playing), from 100 to 4000 ms. Each press of a hi-speed key changes the scroll speed by the same ratio, `6^(1/34)` ≈ 5.4 %, through the visible times `round(100 × 6^(k/34))` ms for k = 0 to 70, a ladder that holds both bounds and 600 ms; a fixed step in ms would change the speed by 4 % a press at 600 ms but 17 % at 150 ms. The scale is fixed once at play start from the chart's initial BPM, so the visible time is exactly the setting at the start BPM. During play notes move through `ScrollMap` positions at that fixed scale: BPM changes speed them up or slow them down and STOPs freeze them, as the chart intends, and nothing ever jumps. This is the base-BPM method of design.md:868 with the start BPM as the base, which needs no main-BPM detection. Alternative: scaling by the BPM in effect at the display time, which keeps the visible time at every BPM but makes the notes jump at each BPM change. Alternative: a continuous visible time (notes placed by time alone), which never jumps but erases the chart's intended speed changes and STOPs. A base-BPM choice other than the start BPM comes when a player asks for it.

### D10. Settings persistence

TOML (design.md:849) in two files, as design.md:646 requires: `device.toml` (the keyboard key config, the controller key config with its controller's model, the three offsets, audio device, master volume, queued audio periods) and `player.toml` (hi-speed, preset file, displayed gauge). Both live in one data root, `%LOCALAPPDATA%\tapestry\`, which also holds `presets\custom.toml` and `records\`.

- The design says nothing about location. Local, not roaming, AppData, because device settings must not follow a profile to another PC and records are large. One root keeps backup simple, and the scopes stay separated by file.
- On first start `custom.toml` is written by serializing `rules::custom()`. At each retry the session checks the file's modification time, and a changed preset is used from that retry on. design.md:632 says files are reloaded "immediately"; stage 1 reloads at the next retry only, which is the earliest point a reloaded preset may be used in play (design.md:633), and no result screen re-evaluates under it yet. PR10 records this stage 1 behavior in design.md "Tuning Without Restart". File watching arrives with the result screen in stage 2.
- Keyboard bindings are shared across keyboards (D6). Controller bindings, by HID usage, belong to one controller (vendor and product id, and on a composite device the interface number of the function), which key config saves with them; only the first connected controller of that model takes part, and other controllers take no part (design.md "Analog Scratch" names the rules). Alternative: the device path or serial, which changes with the port or is missing on many controllers, and would put a unit's identity in `device.toml`.
- Alternative: one settings file. design.md:646 rejects it. Alternative: the registry, which is not human-editable and does not fit the presets distributed as files.

### D11. How key sound and frame latency are measured and displayed

**Origin of every figure.** Each `PhysicalInputEvent` carries its raw receive time. The evaluator copies it, unchanged and not offset-adjusted, into the events an input produces (`JudgeEvent::origin: Option<TimeUs>`; `None` for deadline events). Sound commands and render effects carry it on. This is data passed through; the evaluator still reads no clock. `origin` is used only for subtraction, never as an identifier: every event of one batch shares it, so the two judgments of a chord have the same origin. Events are identified by `JudgeEvent::seq`.

An overlay toggled by a key shows p50, p99 and max over the current play. Values sit in preallocated whole-play histograms (exact below 64 µs, then 32 buckets per power of two, so a percentile is within 1/64 of the exact one; count and max exact), so nothing allocates. The same figures are written next to each saved log as `<record>.measure.toml`, numbers only.

| Input → judgment (µs) | Logic processing time − origin | design.md:453 |
| Finalization delay (µs) | Logic time − watermark at each advance | design.md:247 |

### D12. Audio clock mapping and drift

Stage 0 found that `IAudioClock::GetPosition` on the development PC's interface advanced a whole period at a time against a current QPC, so the spike mapped samples to time from the buffer events instead. `MixClock` keeps the least-late wake of a window, and the first queued frame (written − padding) is mixed one period after it (spike/app/src/audio.rs:756-764; spike/core/src/engine.rs:282). Stage 1 uses that mapping, re-anchored on every period, and records `GetPosition` only as a diagnostic. The spike still ran a real-time resampler, so it is evidence for the mapping, not for the complete path without one.

- **Key sounds.** A command is scheduled at `max(frame_at(origin), first unwritten frame)`. With two periods queued ahead of playback (design.md:394), the first unwritten frame is about two periods past the wake that reads the command, so receipt to start is roughly 2–3 periods, depending on where in a period the press lands. That matches stage 0's 26 ms at a 10 ms period. The head of a sound is never cut to catch up (design.md:406).
- **Queued periods.** Two by default. On the development PC's interface the driver's block size and the 441-frame engine period beat every 2.56 s, and about one session in three locks into a phase that underruns at each beat; three queued periods removed it in every test, for one period (about 10 ms) of key sound latency. So a play with an underrun from its chart time 0 on (after the countdown, its first second, where the stream settles), however the play ended, makes the following plays queue three: `queued_periods = 3` in `device.toml`, shown on the end screen and beside press → sound in the overlay. The audio thread applies a change on the running stream between plays, before recording opens, and answers with what the output keeps (the buffers are sized for three when the stream opens, so nothing allocates). `IAudioClient3` chooses its own buffer, 970 frames on that interface, just over two periods, at a shortest period that is also its default; such a stream is opened through `IAudioClient` at that period with a buffer of three and a half periods instead, which adds no latency, since only the queued frames do. A device whose shortest period is shorter keeps it, and its queue deepens only as far as its buffer holds; an output that already failed is not asked, and the play ends on the failure as before. Nothing lowers it but the player editing `device.toml`. Alternative: always three, a period of latency on devices that do not need it. Alternative: re-creating the stream, which a change of the running stream's queue makes unnecessary.
- **BGM** events are scheduled from chart time through the same mapping, minus the audio output latency offset (design.md:167-171, 387).
- **No real-time resampling in stage 1.** Re-anchoring keeps every sound start on the QPC timeline. Drift then shows only inside one long, already running sound, about 9 ms over 3 minutes at 50 ppm. Measured drift (ppm) is recorded per play. Alternative: the PI-controlled variable-ratio resampler of design.md:874, which costs the resampler's ≈1 ms on every key sound and a controller to tune, before a long-sound drift problem has been heard. Trigger to build it: a chart whose single-file BGM is heard drifting against key sounds, or recorded drift that would reach a refresh over a song.
- **Everything decoded is held in memory**, within the caps of D14. A chart that exceeds them is refused with the reason (design.md:505); read-ahead streaming (design.md:384) is built when a chart the developer wants to play is refused.
- PR11 updates design.md before the code depends on it (AGENTS.md: "update design.md first"): the audio row of design.md:131, "Aligning Audio to the Judgment Timeline" (design.md:154-161), the long-sound paragraph (design.md:384, now fully decoded and bounded in stage 1), and the "Audio clock correction" row (design.md:874).

### D13. Lifecycle, completion, and other stage 1 rules

- **Lead-in:** chart 0 µs is 1 s after the countdown starts, so the first note cannot arrive before the player is ready (tuned by playing). Retry reuses decoded audio and GPU resources and only resets the session (design.md:509).
- **Evaluation completion:** the evaluator's final deadline is the latest applicable deadline of the chart (tap miss deadlines, LN release deadlines, mine times). Evaluation is complete when the global watermark passes it, not when QPC time does; with a positive input offset these differ. The evaluator then emits `SongEnd`.
- **Abort:** retry, quit, focus loss, removal of the last participating device, suspend/resume, and input beyond the recording capacity (D8) abort the play. An abort ends at the last watermark the evaluator had already finalized, with no further advance; staged and later events stay in the record, while recording capacity remains, but are not evaluated. The record stores that finalized watermark with the end status "ended midway". Re-evaluation runs `advance_to(finalized)` instead of to the end and is compared with the live stream over that prefix only. Suspend/resume also sets `incomplete` with the reason "suspend" (design.md:115), because the clock jumped during it, and a capacity overflow sets it with the reason "overflow". The other aborts do not themselves set `incomplete`; a flag already set by a queue overflow or the source limit is preserved. A system control or focus loss seen in a step is handled before that step advances, so a retry in the step that would emit `SongEnd` ends the play midway. A play aborted before its first advance has no finalized watermark and saves no record.
- **Recording closure:** on `SongEnd`, recording closes and its finalized watermark is frozen. The input thread appends no judgment input after that, so the recording window, and its capacity, ends at finalization.
- **Audio tail:** `game` ends the play screen when evaluation is complete and the audio engine reports no active voice and no BGM event left. This is session policy, not evaluation. During the tail, retry and quit are still handled as system controls, but nothing is appended to the record.
- **Debounce** is not implemented. Keyboards do not bounce, and controller firmware usually debounces. The device profile gains it with a format version bump when a device needs it (design.md:201, 871).
- **`#RANDOM`** uses our own SplitMix64 with the seed recorded. Alternative: `rand`, whose output streams may change across versions and would break replays.
- **Offsets:** input latency can change only between plays (the log has no offset change segments; design.md:183-191). Display latency and volume change anytime, since they do not affect judgment.
- **Allocation check:** the counting allocator (design.md:860) is our own, ported from spike/app/src/alloc.rs:1-10. It is a `#[global_allocator]` in the allocation test binaries and, under `dev-tools`, in `player`.

### D14. Loading limits and file confinement

Charts and sounds are untrusted input (design.md:718). Every limit is checked before the work it bounds, and exceeding one is a load error with the reason.

- Chart text: file size, line count, object count, measure ≤ 999, decimal digits and exponent (PR2, D3); the exact time's denominator ≤ 16384 bits (D3); `#RANDOM`/`#IF` nesting depth ≤ 16 (PR3); chart duration ≤ 60 min, checked on the resolved chart before any capacity is sized from it (PR2). Real charts sit far below each.
- Sound paths: a `#WAV` name that is absolute, rooted, drive-prefixed, UNC, or contains `..` is rejected before joining. After the extension fallback (`.wav .ogg .flac .mp3`), the candidate is canonicalized and must still lie under the canonicalized chart folder, which catches links and junctions. An escape is a load error, not a skipped sound (PR2).
- Audio decoding: at most `min(available cores, 4)` decode threads; each file at most 128 MiB; each sound at most 10 minutes of frames at the device rate; the whole bank at most 512 MiB of decoded i16; source and device rates 8–384 kHz. Limits are checked against the file size and the container's frame count before decoding and against a running count during decoding. Each worker finishes one file (read, hash, decode or drop as a duplicate) before taking the next and drops its raw bytes when done; a sound being decoded is charged to the bank cap for the PCM it has allocated (source buffer, both buffers while one grows, source plus converted while converting), and that charge and its declared share are returned if decoding fails. The caps bound raw file bytes in flight (workers × 128 MiB) and the decoded PCM (512 MiB); the decoder's own workspace is not bounded, a known limitation recorded in design.md "Threat Model" (PR11).
- Replay decoding: compressed size, declared uncompressed size ≤ 64 MiB (checked before decompressing, and decompression stops at it), section lengths against the remaining bytes, and event and source counts against fixed maxima (PR7). Bindings and axes are counted against the evaluator's limits, per source and in all, as each count is read and before anything is allocated for it: at most 256 buttons and keys and 8 axes per source, 1024 and 16 over every source. The evaluator refuses a profile beyond them too, and finds an input's axis by binary search over its source's axes, so a log that declares many controls cannot make conversion slow (PR18). Recording: a play reserves its whole recording window before the countdown (D8), never less. The policy (`game::Reservation`) counts what the constructors allocate: per input of the capacity, the evaluator's input ring, each source's staging, the merge and the record, and `Evaluator::max_events` worth of output, audio commands and the live copy of the events (2 + gauges events per input); and, fixed, the chart's share of those events (its notes, mines and song end), the render effect queue, 64 bytes per chart object for the evaluator's tables and 64 KiB for small parts. The budget is 512 MiB. With one keyboard and two gauges that is 680 bytes an input and about 790 thousand inputs: 54.8 minutes for a keyboard alone (240 edges a second). Each further source adds its staging, 24 bytes an input: a controller with seven buttons and a turntable axis reporting without pause (1240 inputs a second) and one keyboard record about 10.25 minutes, and with seven keyboards 8.5 minutes (before the fixed costs). One axis over the longest chart allowed here (60 minutes, 3.6 million reports) would need about 2.5 GiB, which is not a sane reservation, so a play whose window needs more than the budget allows, its fixed part included, is refused before its countdown with the inputs it needs and the inputs that fit, never cut off midway. About 10 minutes with a turntable axis is a known stage 1 limit: the output is reserved for the worst case of every input, because it is not streamed out in bounded steps, and a bound by presses instead of reports would be unsound without such streaming. Bounded output streaming lifts it. Input beyond the capacity at run time aborts the play at the last finalized watermark and marks the log incomplete (D8). The budget keeps every record within what the standard decoder reads at the worst-case 22 bytes an event (a test pins it). Raw Input packets are read up to a 4 KiB report; a larger packet, or a read that fails, is lost input and marks the log incomplete (PR18).
- Axis report rate: the recording reservation counts each lane-bound axis its source declares at 1000 events a second of the shared capacity (D8), a second known stage 1 limit. An axis is recorded at its first absolute value, then at each changed value or nonzero delta, jitter included. A moving axis spends capacity fast, and a still one spends little. A device polling faster than 1 kHz is recorded report by report, never merged within a wake (design.md "Analog Scratch"). It can exhaust the capacity within a play of ordinary length. Such devices are uncommon: polling at 2–8 kHz is mainstream for mice and keyboards, not for dedicated controllers. Polling rate does not raise the cost of buttons or keys. HID buttons are recorded at state changes, and keyboard packets as they arrive, auto-repeat included. Mice are not read. Take the three-minute play of PR18's capacity test: one source, nine buttons, one axis, about 40 button edges a second, and an axis that changes on every report while it moves. Its play aborts once the axis has moved for more than about 15% of the play at 8 kHz, 30% at 4 kHz or 60% at 2 kHz. Continuous movement at 8 kHz exhausts the whole shared capacity in about 28 s. Coarse encoder resolution lowers the changed-report rate, and jitter at rest raises it. Reserving 8 kHz per axis under this reservation (about 650 MiB for two minutes) would refuse ordinary axis plays before the countdown. A larger capacity waits for the same bounded output streaming, with the replay decoder bound kept as its own admission check.

## 6. Risks that change the plan

- **Press-to-sound in shared mode**: on a device with a fixed 10 ms period, the internal path is about 2–3 periods, 26 ms p50 in stage 0 (S0 results), and it may feel heavy. This is not fixed inside stage 1. The trigger for rebuilding the output path is the developer reporting key sound lag on the exit chart; the low-latency path (exclusive mode, ASIO, design.md:395) then becomes the next variation.
- **No drift resampling (D12)**: rebuild trigger as stated in D12.
- **Focus-loss abort**: aborting on every focus loss is strict. If the developer finds it gets in the way (for example a notification stealing focus), pausing with a recorded gap is the rebuild. That needs an operations stream and a log version bump, not a change to the watermark rule.
- **Raw Input registration**: winit must not register device events (PR13). A controller that reports in a vendor format instead of standard HID usages needs its own input adapter, which is the planned input extension point, not a core change.
- **Crate split (D1)**: if a `cfg(windows)` dependency leaks into the Linux build of `input` or `audio`, CI's portable job fails. The fix is to move the Windows part into its own Windows-only crate behind the same traits.
- **Evaluator internals**: if a stage 2 preset cannot be expressed with D4's streams and D7's axes, the evaluator internals are rebuilt behind the unchanged contract (design.md:291-297). The log format is not affected, because it records input, not judgments.
- **DXGI statistics**: if they are invalid most of the time on the development PC, the in-game "on screen" figure stays N/A and PresentMon (PR17) is the only frame evidence. This is acceptable because the statistics are diagnostic by design (design.md:134).
- **GPU power state**: measurements run with the driver's maximum performance setting and record it (design.md:497-501). The default-settings behavior stays an open question.

No decision is needed to start. The developer chooses the exit chart and the device it is played on.

## 7. What the developer verifies at stage exit

1. On the development PC (WQHD 240 Hz, VRR off, maximum performance power setting), set up keys with `tapestry keys` on the device you play with.
2. Play one chart from your own collection to the end with `tapestry play <chart>`. Key sounds and the bomb and judgment feel immediate, and the notes never visibly hitch.
3. Press retry mid-song and at the end. Play restarts at once, and the aborted play is saved as ended midway. Hold a lane key while pressing retry and let go after the restart: nothing is judged from the release.
4. Change hi-speed, volume and display offset during play, and input offset on the end screen. Each takes effect, and `device.toml` and `player.toml` keep them after a restart.
5. Edit `presets\custom.toml` (for example widen GREAT), retry, and see the change in judgment.
6. Open the overlay during play. It shows input → judgment, press → sound scheduled with the device period, press → on screen, lost refreshes (frame statistics), render CPU p99 and max, and underruns. After play the same figures are in `.measure.toml`.
7. Run `tapestry measure play <chart>` once and read the PresentMon lost-refresh count for the play.
8. Alt-tab during play. The play stops as ended midway, and nothing typed outside the game is recorded.
9. Unplug the keyboard you are not playing on during a play. The play continues and no key is left held.
10. Optional: run the local chart sweep over your collection and look at the warnings.
